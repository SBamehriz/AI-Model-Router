# Verification

Verification is reproducible from the repository root with Node.js 22.13 or newer. The commands use isolated data and do not require provider accounts.

```sh
npm ci
npm run check
npm run test:smoke
npm run test:simulation
npm run test:load
npx playwright install chromium
npm run test:browser
npm audit
```

## Automated coverage

The review on September 20, 2026 passed the whole suite, 38 API test files and 5 dashboard test files, on Windows 11 with Node.js 24.14.0, the combination CI covers alongside Linux on Node.js 22 and 24. Lint, type checks, both production builds, the smoke check, and the HTTP simulation passed. The dependency audit reported zero known advisories. Those two file counts are checked by the suite itself, so they cannot quietly stop being true. The number of individual cases is deliberately not printed: it cannot be counted from inside the run, so it would be a figure nothing verifies. These results describe that review and should be rerun after changes.

The quality gate runs lint, TypeScript checks, API test coverage, dashboard display tests, and production builds. API tests cover routing constraints, classification, fallback, adapter translation, validation, authentication, request storage, catalog refresh, and migrations. Dashboard tests cover the pure display logic underneath the pages: money and duration formatting, the daily chart series, the client configuration snippets that Settings, the guide and the integration documentation all copy from, and the sentence every page gives a failed request, which once let the browser's own "Failed to fetch" through on one page while the page beside it explained the same failure. Rendering itself is covered by the browser sweep rather than by a component test.

The smoke test starts the built server and checks the dashboard routes, provider setup, router key scopes, revocation, JSON, SSE, readiness, and request tracing. It also fails if the run emits any deprecation warning, since an operator told to run `npm start` should not be shown a notice they cannot act on, and a notice naming a removal is how a major version becomes a surprise.

The simulation starts a built router and local provider fixtures over actual HTTP sockets. It creates custom providers and a router key, then runs the same client checker used for a real connection. It exercises text, function calls and results, buffered streaming, provider rejection, malformed replies, retry, fallback on both completion paths, invalid inputs, and request body limits. A fallback answer is checked against the request log as well, so the level and provider it reports are the ones that were stored.

The simulation also restarts the router with the same database, verifies saved credentials still work, revokes the router key, removes providers, and restarts again. The revoked key remains rejected and unauthenticated access stays closed. It checks that provider secrets and router keys are absent from returned Settings data, database plaintext, and captured server output.

## Live provider review

The September 18, 2026 review was the first to run against paid provider accounts rather than fixtures, using Gemini and OpenRouter keys. Both completion paths answered: `/v1/chat` and `/v1/agent-step` through the original adapters, and `/v1/chat/completions` through the compatible ones, covering a JSON completion, a buffered SSE stream with usage and `[DONE]`, and a function call and result round trip. Recorded cost was recomputed from the stored token counts and catalog rates and matched to the last decimal on both providers.

Experimental boost ran against real providers as well. Below the complexity threshold it skipped decomposition and answered through normal routing, as documented. Above it, with a manager model named explicitly, it decomposed the prompt into five sub tasks, ran them in parallel, synthesized an answer, and reported per task models, costs and latencies. A run whose manager call failed upstream fell back to normal routing and still answered.

Catalog entries were checked against what the providers publish now. Both Gemini model IDs exist on the live API with the context window the catalog claims, and their prices match Google's published rates. The OpenRouter listing was compared entry by entry, which is where the pricing provenance defect and two stale context windows were found.

A second live pass concentrated on what the first could not reach. Eighty concurrent requests against Gemini's free tier produce a real rate limit rather than the moderate burst that did not: fifteen answered and the rest came back 429 from the provider, 248 of them counting retries. Those were being reported as `502 provider_error`, and both paths now answer `429 provider_rate_limited`, verified by repeating the burst. A burst that mixes a 429 with any other failure still answers 502, which one request out of thirty five did.

A real safety refusal was reached by lowering Gemini's own thresholds to `BLOCK_LOW_AND_ABOVE` rather than by writing something harmful. Two prompts came back with `finishReason: SAFETY`, the router raised a refusal with reason `safety`, and the captured body is now a test fixture: a real block carries `content: {}` with no parts array, so any reader that looks at the content before the finish reason would see a malformed body and retry a refusal elsewhere.

Sixty simultaneous completions produced sixty rows with sixty distinct request IDs, sixty routing decisions including the failures, no row breaking its own invariants, and no cost that differed from recomputing it from the recorded tokens. A router key revoked while one of its requests was upstream let that request finish and rejected the next with 401, which is what the documentation promises.

A twelve minute paced run answered all sixty requests, and a catalog refresh executed against the same database mid-run while traffic was flowing: the Groq entry kept its own price and `data_source: config`, so the pricing rule holds under a concurrent write rather than only in isolation. The database stopped growing after the first minute, so the write-ahead log is checkpointing, and open connections stayed flat. Resident memory rose about 6 MB over the run and did not come back at idle, so the question was put to a harder test: two thousand requests against a process capped at a 96 MB old space all succeeded with no out-of-memory, and growth per batch fell from 43 MB to 7. That rules out an unbounded JavaScript heap, though it does not rule out slow growth over hours.

A saved key decrypted through the same path the server uses, on a fresh process reading `credentials.key` from disk. The server log, `/health` and `/v1/models` were scanned for the provider key, the router key and the general shape of each, with no match. An instance given a deliberately invalid Gemini key returned `502 provider_error` after trying both Gemini models in turn, recorded both attempts, and repeated none of the upstream error text. A disposable router key was created, used, revoked through the administrator API, and then rejected with 401 on both model discovery and completions without a restart.

## Load, memory and concurrency

The figures in this section come from `npm run test:load`, so anyone reading them can reproduce them. It starts the built server under `--expose-gc` with a probe that answers a heap request over the process's own IPC channel, runs a warm-up, a sustained phase at a set number in flight, an idle settle and a burst of simultaneous requests, then reads the stored rows back and checks them against themselves. It fails on a request that went unanswered, a request id handed out twice, a heap that did not come back, a row that is not its tokens times its model's rate, a request with no routing decision, a row whose timing could not have happened, and a row calling simulated traffic live. The defaults are small enough that CI runs it on all three matrix entries, so those invariants are checked on Linux and Windows on every push rather than only on a developer machine; `LOAD_TEST_REQUESTS` raises it to a long reading.

Two properties a row check might reach for cannot fail and so are not checked. `tokens_total` and `savings` are generated columns, so SQLite recomputes them from their inputs and refuses a direct write, and comparing either to its own definition is a line that reads as a check and is not one; counting distinct ids is the same, since `id` is the primary key. Every check that is made is proven by moving a row underneath it, and the heap budget and a refused request the same way. The summary is guarded as well: a run where nothing answered reports the refusals it is holding rather than looking for a median in an empty array, and the burst's queueing is kept out of the sustained percentiles, which it would move from 262 ms to 1687 ms.

The headline reading, repeated on a second machine and a second operating system. On Linux with Node 22.22 and four cores: 53,200 requests, every one answered with no id repeated and 53,200 rows written; 214 a second over 234 seconds at fifty in flight, median 253 ms and ninety-fifth percentile 262 ms; three thousand simultaneous requests all answered in 8.6 seconds; post-collection heap between 19.8 and 21.6 MB across twenty-two readings, 20.5 MB after warm-up and 20.8 MB after fifteen seconds idle, against a 16 MB budget. Every row recomputed, and `integrity_check` and `foreign_key_check` came back clean. The Windows readings this repeats were 185 to 209 a second, a median of 255 ms, and a band of 18.3 to 20.8 MB. Two machines, two operating systems, overlapping bands, and a run that is now reproducible from this repository by anyone.

CI records the same check on every push. The default run passed on all three matrix entries. The Windows runner, two cores, answered 5,700 requests with no id repeated and 5,700 rows, at 124 a second over 40 seconds at fifty in flight, with 500 simultaneous requests all answered in 3.5 seconds and a post-collection heap of 19.9 to 23.1 MB across twelve readings that ended 1.7 MB lower than it started. A slower machine moves the throughput and not the retention, which is the figure the check exists for. The five hundred at once are worth noting on their own: an earlier measurement lost 468 of a thousand to ECONNREFUSED on Windows loopback and traced it to its own client's connection pool, and nothing of the sort appeared here.

Memory was measured from inside the process rather than inferred from resident size, because resident size cannot answer the question: the allocator keeps pages it has already freed, so it rises under load and stays risen whether or not anything is retained. Running the built server under a harness that forces collection before each sample, fifty thousand requests held post-collection heap inside a 2.5 MB band, 18.3 to 20.8 MB, ending lower than it started, while V8's heap total went past 150 MB under load and fell back once the load stopped. A flat heap beside a collapsing heap total is not a leak, and an earlier reading that called this inconclusive was watching the wrong number.

That run was repeated on the current build after further change, including moving the authorisation guard into an earlier request phase and replacing the logging option. The reading did not move: the same fifty thousand requests, all answered, and the same flat post-collection band. Three thousand simultaneous requests again answered every one with three thousand distinct ids. Elapsed times from that repeat are not reported: the machine suspended during it, so wall clock measured sleep as much as work. A shorter run on a quiet machine, under forty seconds so a suspend could not hide inside it, gives the current figure: five thousand requests with fifty in flight at 185 to 209 requests per second, every one answered, median 255 ms, with the ninety-fifth percentile between 270 and 440 ms depending on whether the database is a file or in memory, which is the cost of the write-ahead log reaching disk. A thousand simultaneous requests are all answered in about a second. That burst figure was harder to get than it should have been. One harness sequence refused 468 of the thousand with ECONNREFUSED, deterministically, and it took separating the client from the server to see why: a fresh client process against the same server at the same moment got all thousand. The refusals were the harness's own connection pool, left in a bad state on Windows loopback by a wide warm-up whose idle sockets timed out during the sustained phase, and never the server. These are numbers from a developer laptop with an editor running, not a claim about a deployment. What they establish is that the work since did not move them.

Concurrency was pushed to three thousand simultaneous completions against simulated providers, well past what a provider quota allows against real ones. Two hundred, five hundred, a thousand, fifteen hundred, two thousand and three thousand all answered every request, with latency rising roughly in step and no dropped connections. Across the fifty thousand rows written by the repeat, and the fifty six thousand of the original run, the database held: every request had its own id and its own routing decision, no row broke its own invariants, no recorded cost differed from recomputing it, and both `integrity_check` and `foreign_key_check` came back clean. With the shared limit left at its default, three hundred simultaneous requests let exactly one hundred through and refused two hundred with the documented headers, so the fixed window neither leaks nor over-counts under load.

Hostile request bodies were sent to all four completion endpoints: null, arrays and numbers where an object belongs, messages of nulls, roles as numbers, four hundred levels of nesting, constructor keys, tool results with no matching call, unicode noncharacters and a lone surrogate. None produced a 500, none put a stack frame or a file path in a response body, and `Object.prototype` was untouched. Those bodies are kept as a test.

Free text that the interface renders was checked for characters that change what it says. A router key name and a custom provider name accepted a right-to-left override and a C1 control, stored them, and returned them for the revoke and remove lists to draw. Labels now drop bidirectional overrides and isolates; message content drops the C1 range but keeps bidirectional marks, which mixed direction prose needs.

The numbers the algorithm document states are checked by the test suite rather than by a person remembering to re-read them. Each worked example is run through the real classifier and estimator and must produce the task and score printed beside it, each priority row must be the weights the router hands out, each task baseline must be the floor the estimator reports, and the attempt cap and both provider deadlines must equal the constants the code exports. Nothing is restated, only parsed, since a restated number is a second copy free to drift. Verified by drifting the document six ways, one per claim: every one fails.

Authorisation was checked by walking every route with every kind of caller against the built server rather than a test harness: seventeen routes, unauthenticated, with a router key and with the administrator key. Three answered an unauthenticated `DELETE` with 400 rather than 401, because the body is parsed between the two hook phases and the guard ran in the later one, so a bodyless request declaring JSON failed in the parser first. Nothing was reachable that should not have been, confirmed by aiming five unauthorised deletes at a real key and finding it still there. The guard now runs before the body is read, and the matrix agrees with the documented rules on every route.

Rejections carry one piece of caller text: a strict schema refusing unknown keys names them. It is contained, since only the administrator key reaches those schemas, nothing logs the messages, and the dashboard neither reads `details` nor contains any `innerHTML`. Those are three properties of other files, so the echo is bounded where it is produced instead: deceptive characters dropped, and a length cap.

Unmatched and hostile paths were probed directly: dotfiles, percent and double-percent encodings, null bytes, and traversal through both slash directions toward `.env`, `credentials.key` and `.git`. Nothing escaped the static root. Sixty wrong keys sent with a different `X-Forwarded-For` on each request still exhausted one budget and then answered 429, which is the intended reading of a header nobody should be able to set for themselves.

## Browser review

The September 2026 browser review drove Chromium against an isolated local instance with seeded sample history. It ran a prompt through the Playground, followed its request link into the log, expanded the saved decision, searched the guide and reached its empty state, unlocked Settings with an administrator key, created and revoked a router key, saved and removed a provider key, and switched themes across a reload.

Layout checks cover all eight pages in light and dark themes at widths of 320, 390, 768, 1024, and 1440 pixels, plus an 812 by 375 landscape viewport. Both normal and reduced motion sweeps passed, for 192 combinations, and all eight pages passed again in both themes with text enlarged to 200 percent. Each render asserts that the document does not overflow sideways and that no console error is raised.

The layout sweep was repeated against an instance holding real provider traffic rather than seeded history, over all eight pages in both themes at the same five widths, and reported no sideways overflow and no console error. It was repeated again after the brand gradient was unified, with the same result. Contrast is checked across the whole interface on every run, not only where a change was made. `npm run test:browser` starts the built server on a throwaway database and drives Chromium over all eight pages in both themes and measures every painted text element against its WCAG floor, 9,914 of them across 36 renders, resolving two things a simpler reading gets wrong: text clipped to a gradient is painted by the background rather than by `color`, so every stop is measured, and a tint over a card over a page is a composite, so layers are collected out to the first opaque one and composited back. A page loaded successfully is only one of its states, and the only one an unattended visit reaches, so it also drives four others: the API failing, a report still arriving, an empty report, and a disclosure opened. The error panel's message sits on a destructive tint that exists in no successful render. All 9,914 pass, and the closest to its floor is the sidebar wordmark at 4.53:1 against 4.5. The count was 10,004 a day earlier; the failed state now refuses the administrator routes as well as the report routes, which reaches the settings page's locked layout instead of its provider list, and the models page reports a failed catalog inside the table's own frame.

CI runs it on Linux on every push, and its logs carry the figures. The first Linux run measured 10,006 text elements against the 10,012 measured here the same day, before the failed state was widened, the same 392 focus indicators and 366 hover states, and the same closest margin, 4.53:1, in 284 seconds, so the figures in this document do not depend on the operating system they were first taken on. That run also printed four deprecation notices that no local run had, all from inside the GitHub actions the workflow used rather than from the project; moving both actions to their current majors took the count to zero on the next push, which passed on all three of Linux 22, Linux 24 and Windows 24. The tool is checked against defects rather than only against a clean build. Pointing the light-mode text gradient back at the filled-shape stops, which is what an earlier revision shipped, is reported at 2.06:1 on eight pages, together with two gradient elements no hand-written case had ever covered. Deepening the error panel's tint is reported between 3.52 and 4.01:1, and every one of those is on a failed state, which is what shows the extra states reach further rather than only measuring more. Real routing is cheap enough that a total can sit below the displayed precision, which is where the summary tiles were found rounding a live cost to a figure that read as zero.

Focus is measured as a colour, not merely as present. An earlier sweep reported every control as ringed by checking that an outline had a style and a width and that a box-shadow string existed, none of which reads a colour: buttons carry Tailwind's outline-none, which is a transparent two pixel outline, and drew their focus with a half-opacity ring that composited to between 2.1 and 2.7 to one. The ring is solid now, and the audit measures 392 indicators against the 3:1 a focus indicator needs, reading both spellings of one and skipping disabled controls, which cannot be focused.

The gap before a page settles is measured too, because that is where two defects had been hiding. Each render is watched for layout shift from before its first paint, summed the way Cumulative Layout Shift is, and allowed 0.025 in total, the boundary between a movement a reader notices and one they do not. That measurement only means something if the gap exists: the server in the run is on the same machine and answers in two milliseconds, less than one frame, so the layout a page shows while it waits was never painted and never moved, and the first version of the check passed a 0.23 shift on the settings page without seeing it. Every answer from the API is now held for 400 milliseconds, which is what a router on another machine takes, and with the gap made visible the check reports that same regression at 0.231 in both themes when it is put back. What it found on the real build: the settings page swapping the unlock form for a banner a fraction of its height once a stored key was accepted, 0.23; the overview replacing a one line notice and a metric strip with their answers, 0.06; the models page inserting the catalog line above its table, 0.02, and its error panel above it, 0.07; and the playground's status line arriving after the page, 0.03 on some loads. Each now holds its frame before the answer arrives and keeps a slot of the same height for an empty or failed one, and the worst of 36 renders is 0.008. The Linux run for that push measured the same 36 renders for layout shift and 9,908 text elements, six fewer than Windows, and passed in 356 seconds, the held answers having added about a minute. A render that does not finish, a navigation that times out for instance, is reported as a failure rather than skipped, since the summary once counted renders from the plan and not from what happened. The first frame's theme is checked on every page rather than one, since one page cannot differ from another today but nothing prevented it, and the browser chrome colour that mobile browsers paint around the page was found hardcoded dark for light theme users and now follows the theme from the same pre-paint script. The first frame check had the same defect the render sweep once had: a check that threw printed a line and was skipped, and the count guarding it is a floor of one, so fifteen of sixteen pages could time out with the run exiting 0. It is a failure now, proven by giving one page a deadline it cannot meet, and the summary says how many of the sixteen ran.

The chrome colour itself is measured rather than maintained. It is declared as a hex in three places, the document, the pre-paint script and the component that follows the toggle, while the background it is meant to match is an `hsl()` custom property, so the browser resolves both on every page in both themes and they have to agree. The dark value had already drifted: `#0E1116` is `rgb(14, 17, 22)` over a background of `rgb(14, 16, 21)`. One part in 255 is not something a reader sees, which is why three copies of it drift quietly; all three now say `#0E1015` and the check is what keeps them saying it.

The gate resolves the browser build matching its own Playwright, which is what CI installs and what a machine with one already provisioned does not have, so `CONTRAST_AUDIT_CHROMIUM` points it at that one. Run that way against Chromium 141, where the pinned Playwright ships 153, it reported the same 9,908 text elements, 392 focus indicators, 366 hover states, 36 renders, 16 first frames, 16 chrome colours and 4.53:1 closest margin as the Linux CI run on its own browser. That is a third machine and a second Chromium major agreeing with the figures above.

The keyboard was walked as well as the layout. Tabbing through all eight pages and reading each stop from the accessibility tree found every stop named and every one carrying a visible focus ring, with three exceptions since fixed: the pie chart put a 200 by 200 stop in the tab order that announced nothing, and two targets sat under the 24 pixel minimum. The same sweep checks heading order, duplicate ids, labelled inputs, captioned tables, and that decorative graphics are hidden rather than announced.

Failure simulations pointed the dashboard at an address with nothing behind it, stalled a completion, and returned a provider error. Each one produced a stated cause, an action to take, and a way back: a named address with the command that starts the server, a retry on an unavailable report, a prompt that can be abandoned and run again, and the provider failure reported rather than swallowed. Empty reports read as a starting point instead of a fault.

The README screenshots come from the running application. Sample history and offline completions are labeled. They are not evidence of paid provider traffic or measured production performance.

## Limits of these checks

Local fixtures verify the protocol and router behavior. They do not verify account credit, permissions, every provider model, an installed OpenClaw gateway, or every OpenAI API feature. The dependency audit reports known advisories at the time it runs. Passing checks does not prove that all possible bugs or vulnerabilities are absent.

The live review covered Gemini and OpenRouter only. The OpenAI, Anthropic and Groq adapters, and every custom provider, are verified against fixtures alone, and that is a settled limit rather than an outstanding task: the project holds no key for any of the three, and their APIs will not answer without one. The Groq entry in particular rests on Groq's published documentation. No installed OpenClaw gateway was involved. The longest run was fifty thousand requests, in about nine minutes on Windows and about four on Linux, followed by an idle settle, with a separate burst of three thousand simultaneous requests. That is long enough to rule out an unbounded heap and a concurrency ceiling, and too short to characterise a week. What CI runs on every push is the same harness at a few thousand requests, which holds the invariants rather than the duration: a long reading is still something a person starts by hand.

Run the [client checks](TESTING-CLIENTS.md) with your own provider and a disposable router key. Then send a message and a harmless tool task from your installed client. Confirm successful live entries in Requests. Revoke the disposable key and verify that model discovery returns 401.
